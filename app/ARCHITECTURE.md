# EduBridge_AI 技術架構

## 資料流

    教師瀏覽器麥克風
      → 約 10 秒的獨立完整音訊，辨識期間暫停收音
      → POST /api/transcribe
      → Whisper 逐字稿
      → 所有學生先看見逐字稿
      → POST /api/scaffold（文字向量檢索已確認教材，最多三段，每段只呼叫一次）
      → 一份結構化 JSON
      → 視覺重點／閱讀鷹架／專注節奏三種私密呈現

三種模式是學生自行選擇的介面偏好，不是診斷標籤，也不會在教師端公開學生的個別選擇。

## 已實作

- 四個可切換的操作介面：教師主控台、視覺重點、閱讀鷹架、專注節奏。
- POST /api/scaffold：一次輸出三種支援模式的結構化欄位；未設定金鑰時使用明確標示的示範整理。
- POST /api/transcribe：僅在伺服器設定 GROQ_API_KEY 後才會將音訊送至語音辨識服務，且拒絕超過 25 MB 或不允許格式的檔案。
- LLM 提示詞限制只可依逐字稿及檢索教材整理，不可推測學生特質、不可新增事實。
- Office 教材在瀏覽器解壓與解析，保留投影片順序／Word 段落；圖片、動畫、講者備註不解析。
- 教材需教師確認；修改後撤銷該段確認，清除快取及舊生成。檢索使用中文雙字詞／英文詞 TF-IDF cosine，相似度低於 0.06 不採用。
- 頂多三段教材提供給 Groq，一次生成三種鷹架；回應格式與引用 ID 做本地驗證，超時或失敗退回原文分句。
- BroadcastChannel 同來源同瀏覽器分頁同步；學生可暫停自己的畫面及匿名求助，並非跨裝置連線。
- 課堂教材與最多 30 段結果只在記憶體，可手動匯出／匯入 JSON；localStorage 只保存閱讀偏好。

## 尚未宣稱完成

- 真實教室壓力測試、端到端延遲與辨識正確率。
- 教師備課時間降低比例、學習成效或無障礙認證。
- 神經語意 embedding、帳號系統、跨裝置同步與資料庫保存。

## 成本與節流原則

為避免三種介面造成三倍 LLM 請求，系統每一段逐字稿僅呼叫一次鷹架 API，回傳三種模式欄位。實際上線前應依帳號方案與模型限額調整音訊切段、佇列與退避機制。

## RAG 演進

競賽 MVP 已有詞彙檢索型 RAG；同義改寫與跨語言檢索仍可能漏取。下一步可將檢索函式換成本地或雲端語意 embedding，保留現有的教材確認、來源 ID、生成與前端介面。引用目前是本段結果層級，尚非每張卡片的逐句證據驗證。
